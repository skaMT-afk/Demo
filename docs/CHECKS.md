# Будущие проверки решений

Это план, не протокол выполнения. Скрипт [smoke.py](../scripts/smoke.py) реализует существенную часть V-01–V-06 и SQL-литерал из V-08. Проверки, не вошедшие в скрипт, выполняются отдельно. [Статус](VERIFICATION.md).

Общая подготовка: отдельная локальная БД, зарегистрированы A (владелец команды и автор), B (исполнитель), C (член той же команды без отношения к задаче), X (посторонний). У A/B/C/X свои сессии. A добавляет B/C, создаёт задачу для B. Сохранять status code, важные поля до/после и commit проверяемой версии. Не сохранять секреты в отчёт.

| ID | Условие и действие | Ожидаемое наблюдение | Автоматизация |
| --- | --- | --- | --- |
| V-01 | GET /api/tasks без токена/со случайным; затем X выполняет logout и повторяет запрос. Отдельно дождаться expiresAt или установить прошедшее ExpiresAt в изолированной тестовой БД | 401 для каждого недействующего токена; действующий токен получает 200; сессия после logout отсутствует в БД | Без токена, случайный и logout — smoke; expiry — вручную |
| V-02 | A/B/C/X читают известную задачу и список. Отдельно запросить случайный UUID | A/B видят задачу; C/X — 404 и отсутствие объекта в списке. Несуществующий UUID — тот же 404 | Основной случай — smoke; случайный UUID — вручную |
| V-03 | A создаёт задачу с authorId/state в JSON, назначает себя; C пытается accept; B пытается accept/return; A — submit. Отдельно PUT/PATCH задачу | 400 на лишние поля/самоназначение, 404 чужому, 403 неверному действию видимого объекта; без изменений. PUT/PATCH — 404/405 | Основные случаи — smoke; PUT/PATCH — вручную |
| V-04 | accept из assigned, пустой submit, повторный submit из review; пройти return→submit→accept, попробовать менять accepted | Некорректный переход 409, пустой текст 400; положительный сценарий 200, версия +1 на переход; терминальное состояние и текст неизменны | smoke |
| V-05 | Сохранить review(v2), выполнить return(v2), submit(v3); отправить старое accept(v2). Из review(v4) параллельно отправить accept(v4)/return(v4) | Старое решение 409 без изменения R2; у пары ровно один 200 и один 409, итог version=5; нет потери обновления | smoke; несколько запусков в разные минуты для повторной проверки, не нагрузочный тест |
| V-06 | X читает/добавляет в чужую команду, B добавляет X, A добавляет B повторно; назначить X исполнителем | 404, 403, 409, 400 соответственно; состав не меняется при отказах. Положительное добавление B/C — 204 | smoke |
| V-07 | Осмотреть Accounts/Sessions в тестовой БД, используя два аккаунта с одинаковым паролем; искать тестовые сырой пароль и токен в БД и логах | Разные salted password hashes, session hash вместо токена, нет сырых секретов. Пароль 11/129 символов отклонён; 12/128 принят | Вручную; не публиковать дамп и токены |
| V-08 | SQL-строка как result; malformed JSON/лишнее поле, title=201/description=4001/result=8001; тело >65536 байт; серия 31 auth-запроса с одного IP внутри окна; имитировать ошибку БД | Литерал возвращается как данные, таблицы целы; 400/413/429 по типу случая; аварийный ответ без SQL/stack/secrets. GET после отказа подтверждает неизменность | Литерал, title и лишние поля — smoke; остальное вручную |
| V-09 | Осмотреть Git/ZIP, compose, .dockerignore; docker compose ps; попробовать соединение с БД с хоста. Перед публичным релизом проверить TLS с другого узла | Нет .env/секретов, нет публикации PostgreSQL, API только loopback. На публичном контуре сертификат доверенный, HTTP не принимает учётные данные | Вручную; TLS только после появления публичного контура |

## Как зафиксировать свидетельство

После реального запуска: дата, commit (`git rev-parse HEAD`), окружение (`docker version`, `docker compose version`), команда, exit code, фактическое наблюдение, интерпретация и ограничения. Успех /health подтверждает сервер и БД, но не объектную авторизацию; успех smoke не доказывает все SR-08–SR-10. Ссылку на GitHub Actions run можно использовать только после фактического выполнения.
