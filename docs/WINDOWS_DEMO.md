# Запуск на Windows и демонстрация EK1

## Что требует курс

[EK1, раздел 4 и пункт 5.3](https://github.com/hse-rbpo-bachelor-2026/course/blob/main/assessment/EK1.md): нужен локально запускаемый сервер/API, команды и простой способ подтвердить работоспособность. Полный CRUD и все пользовательские сценарии не требуются; число функций само по себе не оценивается. Для подтверждения может использоваться простой endpoint или минимальный сценарий. Дополнительные устные указания преподавателя следует учитывать отдельно.

В проекте уже реализованы регистрация, вход, команды, создание/чтение задач и переходы submit/accept/return. Удаление задач не входит в текущую модель и ради аббревиатуры CRUD не добавляется. Для защиты показываем несколько работающих запросов, а не все функции.

## 1. Подготовить окружение один раз

Нужны Docker Desktop (Linux containers, WSL 2) и Python 3.10+. Отдельная установка .NET, PostgreSQL и pip-пакетов не нужна: сервер и БД работают в контейнерах, Python нужен лишь для демо-клиента.

Официальная инструкция установки: https://docs.docker.com/desktop/setup/install/windows-install/

1. Проверь Windows командой winver. Установи поддерживаемую твоей системой версию Docker Desktop по официальной инструкции; выбери WSL 2 backend.
2. Если установщик сообщает об отсутствии WSL, открой PowerShell от администратора, выполни `wsl --install`, перезагрузи ноутбук. Если WSL уже есть, проверь `wsl --version`; обновление — `wsl --update`. Следуй требованиям установщика к виртуализации.
3. Запусти Docker Desktop и дождись готовности Engine. Используй Linux containers.
4. В обычном PowerShell проверь:

```powershell
python --version
docker version
docker compose version
```

Если `python` открывает Microsoft Store или не найден, проверь `py -3 --version` и в дальнейших командах замени `python` на `py -3`. `docker version` должен показать и Client, и Server. Ошибка Server обычно означает, что Docker Desktop ещё не запущен.

Если на диске C мало места, проект можно распаковать на D. Это само по себе не переносит образы и диск Docker: их расположение проверяется отдельно в настройках Docker Desktop.

## 2. Скачать актуальный проект

Открой https://github.com/skaMT-afk/Demo под своим аккаунтом → Code → Download ZIP. Распакуй, например, в `D:\Projects\Demo`. Открой терминал именно в папке, где находятся compose.yaml и Dockerfile (не во внешней папке архива).

Если уже есть Git-копия, получи изменения через `git pull --ff-only`; сначала сохрани свои изменения. Старый otche_nash_EK1.zip не содержит нового scripts/demo.py.

## 3. Первый запуск дома, с интернетом

```powershell
python scripts/init_env.py
docker compose up -d --build
python scripts/smoke.py
```

Первая сборка загружает образы и зависимости и может занять несколько минут. Продолжай после завершения предыдущей команды без ошибки. Ожидается `PASS: ...` от smoke. Скрипт init_env сохраняет существующий .env; его нельзя отправлять в Git.

Открой в браузере http://127.0.0.1:8080/health — ожидается JSON со status=ok и database=reachable. Это настоящий ответ сервера с проверкой БД. Графического интерфейса приложения/Swagger в этой версии нет; для остальных запросов используется демонстрационный HTTP-клиент ниже.

## 4. Репетиция и показ

```powershell
python scripts/demo.py
```

Скрипт останавливается перед каждым шагом. Объясни действие, нажми Enter, покажи URL, тело запроса, HTTP-код и JSON-ответ. Все обращения идут в работающий API, ответы не подставлены заранее. Тестовые аккаунты и команда создаются обычными ручками API; секреты скрыты.

| Шаг | Ручка | Что объяснить |
| --- | --- | --- |
| 1 | GET /health | Сервер запущен, PostgreSQL доступна |
| 2 | POST /api/teams/{id}/tasks | Автор создаёт задачу, 201, состояние assigned |
| 3 | GET /api/tasks/{id} | Исполнитель читает сохранённую задачу, 200 |
| 4 | POST /api/tasks/{id}/submit | Сохраняются результат и review, версия становится 2 |
| 5 | POST /api/tasks/{id}/accept от исполнителя | Сервер отвечает 403, состояние не меняется |
| 6 | Та же ручка от автора | 200, accepted, версия 3 |

Для короткого подтверждения запуска достаточно показать health и создание/чтение; остальные шаги — готовое продолжение по вопросу преподавателя. Полный сценарий занимает примерно 1–2 минуты без долгих объяснений. Успешный итог — DEMO PASS. Автоматическая репетиция без Enter: `python scripts/demo.py --auto`.

Это изменение через предметные команды, а не универсальный CRUD. На защите полезно объяснить, почему исполнитель не может принять свою работу и почему нельзя произвольно установить state.

## 5. В день защиты

Запусти Docker Desktop заранее. В той же папке с тем же .env выполни:

```powershell
docker compose up -d --no-build --pull never
python scripts/demo.py
```

Заранее проверь эту последовательность без интернета: контейнеры и собранные образы должны оставаться на ноутбуке. Если образ отсутствует, офлайн-запуск не получится — сборку нужно сделать дома. Не очищай Docker и не выполняй down -v перед защитой. Проверь /health в браузере.

Завершение с сохранением БД: `docker compose down`. Каждый новый demo создаёт отдельные тестовые данные. После многократных запусков за минуту возможен 429: дождись следующего минутного окна.

## Если не запускается

- `docker` не найден: установи Docker Desktop, заново открой терминал.
- Cannot connect / daemon is not running: запусти Docker Desktop, дождись Engine.
- WSL/virtualization error: пришли точный текст/скриншот; нужны сведения о Windows и WSL.
- Файл compose не найден: терминал открыт не в корне распакованного проекта.
- Connection refused: проверь `docker compose ps`, затем `docker compose logs --tail 60 api` и `docker compose logs --tail 60 db`.
- Порт 8080 занят: в compose замени 127.0.0.1:8080:8080 на 127.0.0.1:8081:8080, выполни `docker compose up -d`, затем `$env:API_URL="http://127.0.0.1:8081"`; адрес браузера тоже меняется.
- API работает, но demo выдаёт ошибку: пришли команду, HTTP-код и текст ошибки, не .env и не токены.

CI подтверждает запуск в Linux-контейнерах GitHub Actions. Установку и успешный запуск именно на твоём ноутбуке нужно подтвердить отдельно.
