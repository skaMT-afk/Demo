# Проектные решения безопасности

Решения описывают выбор и его ограничения. Код подготовлен; динамическая проверка не выполнена в среде подготовки. V-* — планы, даже если для части уже написан исполняемый smoke-скрипт.

## D-01. Серверная сессия и объектная авторизация

**Контекст:** T-01/T-02/T-03/T-05; SR-01–SR-05, SR-07, SR-08. Глобальная роль «участник» не отвечает, может ли конкретный пользователь принять конкретную задачу.

**Решение:** 32 случайных байта bearer-токена; в БД только SHA-256 и срок 1 час. Middleware на каждом запросе находит действующую сессию; UserId берётся из неё. Только Authorization: Bearer, без cookie/query token. Logout удаляет текущую сессию. Операции над командами/задачами требуют аутентификации. Чтение задачи требует членства и отношения author/assignee; список использует тот же предикат. Добавление участника — только OwnerId команды. Submit — только AssigneeId, accept/return — AuthorId. При создании автор берётся из сессии, назначение самому себе запрещено. DTO содержат только изменяемые клиентом поля, неизвестные JSON-поля отклоняются. Автор/исполнитель/команда уже созданной задачи неизменяемы.

**Обоснование:** решение применяется независимо от клиентского UI. Владелец команды не получает неявное право читать все результаты. 404 для невидимого/несуществующего объекта не раскрывает его наличие; 403 используется при запрещённом действии над видимым объектом, 401 — при отсутствии сессии.

**Альтернативы сессии:** JWT сокращает обращения к БД, но logout/отзыв до истечения потребует denylist или короткого TTL с refresh-процессом. Для маленького одного API выбрана серверная сессия с немедленным отзывом новых запросов; цена — чтение БД на каждом запросе. SHA-256 подходит для случайного 256-битного токена, но не используется для низкоэнтропийных паролей.

**Проверка:** [V-01, V-02, V-03, V-04, V-06](docs/CHECKS.md). Сценарии используют A/B/C/X; важно проверять не только статус, но и отсутствие данных/изменений.

**Ограничения:** токен предъявительский — его кража даёт права до отзыва/истечения. Требуется TLS вне localhost. При появлении браузерного клиента нельзя без анализа переносить токен в localStorage. Cookie-аутентификация потребует отдельного CSRF-решения. Выход не отменяет запрос, уже прошедший аутентификацию. Отзыв членства пока не реализован; при его добавлении проверяется согласованность с одновременно идущими изменениями.

**Где:** [Security.cs](src/TaskFlow.Api/Security.cs), [Program.cs](src/TaskFlow.Api/Program.cs), FindVisible и фильтр списка.

## D-02. Команды перехода и оптимистическая конкурентность

**Контекст:** T-03/T-04; SR-04–SR-06. Принятое решение должно относиться к тому результату, который видел автор. Пограничный случай раскрыт в [THREATS.md](THREATS.md).

**Решение:** вместо PATCH state доступны submit/accept/return. Клиент передаёт version из GET; сервер проверяет роль, состояние и соответствие version. EF Core Version.IsConcurrencyToken добавляет исходную версию к условию UPDATE. Результат, состояние и увеличенная на 1 версия сохраняются одной операцией SaveChanges/транзакцией. Если строку успел изменить другой запрос, DbUpdateConcurrencyException переводится в 409. Клиент перечитывает объект, показывает новый результат человеку и лишь затем отправляет новое решение; автоматический повтор accept с новой версией запрещён на уровне клиентского сценария.

**Инварианты:** assigned/rework допускает submit; review допускает accept/return; accepted терминален. review замораживает результат. Версия растёт при каждом успешном переходе. Запрос со старой версией не изменяет ничего.

**Сравнение применимых альтернатив для одного свойства — защиты приёмки от гонки:**

| Способ | Что обеспечивает | Цена и ограничение в нашем продукте |
| --- | --- | --- |
| Выбранный: Version в условном UPDATE | Из двух изменений одной версии фиксируется только одно; старое решение отклоняется | Клиент обрабатывает 409; каждый путь записи обязан увеличивать версию; возможен конфликт при частых изменениях |
| SELECT FOR UPDATE внутри транзакции + клиентская version | Сериализует изменения строки и после блокировки проверяет виденную пользователем версию | Дольше удерживает соединение/блокировку; нужны таймауты и порядок блокировок; подходит при высокой конкуренции и сложных связанных обновлениях |

Простая серверная блокировка без клиентской версии не решает сценарий «R1 был заменён R2 до запроса»: поэтому она сама по себе не достаточная альтернатива. In-process lock не выбирается: не работает между экземплярами API и при прямом доступе к БД. Для коротких обновлений одной задачи и небольшой команды выбран оптимистический вариант. Если появятся атомарные операции над несколькими задачами или частые конфликты, оценим транзакционные блокировки заново.

**Будущая проверка:** [V-04/V-05](docs/CHECKS.md), включая последовательный stale accept после доработки и две одновременно отправленные команды. После них GET должен показывать один допустимый результат и увеличение версии ровно на 1.

**Ограничения:** не защищает от администратора БД и путей записи, обходящих concurrency token. Массовые SQL UPDATE должны отдельно включать версию. Операции членства не имеют такой конкурентной модели; удаление членов не поддерживается. Два сетевых ответа могут потеряться — клиент перечитывает состояние, а не предполагает неуспех записи.

**Где:** [Models.cs](src/TaskFlow.Api/Models.cs) (IsConcurrencyToken), [Program.cs](src/TaskFlow.Api/Program.cs) (submit/Decide/409).

## D-03. Ограничение ввода, хранение секретов и локальное окружение

**Контекст:** T-06–T-09, SR-08–SR-10. Компрометация данных/конфигурации и перегрузка не покрываются одной объектной авторизацией.

**Решение:** ASP.NET PasswordHasher (PBKDF2 с солью, 210000 итераций), ограничение длины пароля и текстов; Kestrel ограничивает тело 64 КиБ. EF Core строит параметризованные запросы. JSON не содержит неожиданных полей; текст возвращается как JSON и не исполняется. Ответы об ошибках не включают SQL/stack trace. Приложение не пишет пароль, токен или строку подключения в логи, логирует тип исключения и trace ID. Для register/login общий fixed-window limit 30/min/IP. Пароль PostgreSQL генерируется локально в .env; .env исключён из Git и Docker context. API запускается непривилегированно, порт доступен только с localhost, PostgreSQL без опубликованного порта.

**Обоснование:** готовый password hasher уменьшает риск самостоятельной криптографии; SQL-параметры сохраняют текст данными, а ограничения снижают цену одного запроса. Loopback соответствует учебной локальной демонстрации. Случайный пароль не распространяется вместе с архивом.

**Проверка:** [V-07, V-08, V-09](docs/CHECKS.md). Включает осмотр хранимых значений/конфигурации и негативные HTTP-запросы. Публичный TLS — будущий deployment gate, не выполненный факт.

**Ограничения и последствия:** EnsureCreated используется только для новой учебной БД. Он не обновляет существующую схему; дальше нужны миграции и отдельная runtime-роль без DDL. Демо-пользователь БД имеет расширенные права; ограничение сети не заменяет least privilege. Production-режим ASP.NET сам по себе не делает эту конфигурацию промышленной. Образы имеют плавающие теги, package lock и аудит зависимостей отложены; перед внешним развёртыванием нужны проверка поддерживаемых версий, TLS, резервирование, лимиты/мониторинг и закрепление образов. Rate limit в памяти сбрасывается при рестарте и не решает распределённый DoS. После первой загрузки внешние сервисы не нужны для бизнес-сценариев.
